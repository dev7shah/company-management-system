Problem & Value Proposition

Why this system replaces legacy spreadsheets and departmental silos

The Problem — Fragmented Spreadsheets
Legacy operational failure points
Before
  • Data Redundancy & Conflicts: Employee, customer, and sales records lived across disconnected Excel spreadsheets with no single source of truth.
  • Severe Security Gaps: Zero field-level access control; staff members could openly view executive salaries, PII, and financial margins.
  • Manual Order Entry Errors: Unenforced pricing rules and manual discount calculations led to severe billing discrepancies.
  • Absence of Intelligence: Management made inventory and revenue forecasts based purely on instinct without historical modeling.
  • Unmonitored Customer Sentiment: Customer feedback was archived in email inboxes and never connected to product development.
The Solution — Integrated CMS Platform
Architectural resolution
After
  • Single System of Record: Relational PostgreSQL schema with foreign-key referential integrity, unique constraints, and ACID transactions.
  • Role-Based Access Control: Strict hierarchy (Admin > Manager > Employee) enforced with stateless JWT cookies and service-level annotations.
  • Automated Order Calculations: Forward-only order state machine with server-side pricing, tax, and discount validation (0–30%).
  • Predictive Analytics Engine: Dedicated Python microservice running Holt-Winters time-series forecasting and K-Means segmentation.
  • Automated NLP Analysis: TextBlob natural language processing classifying review polarity and extracting aspect sentiment scores.

MOD 01
Authentication & User Access Management
Stateless JWT authentication, password hashing, and role-based permissions
All Roles
Implemented Capabilities
  • Stateless JWT Authentication: Issues HS256 signed JSON Web Tokens with 30-minute expiry containing user ID, role, and unique jti claim.

3. Enterprise Security Controls (8)

Hardened security architecture preventing common web vulnerabilities

1. JWT Cookie Protection

JWT tokens stored in httpOnly, Secure, SameSite=Strict cookies to prevent client-side JavaScript theft via XSS.

2. BCrypt-12 Hashing

Passwords hashed with BCrypt at work factor 12. Password hashes are never written to logs or returned in DTOs.

3. Brute-Force Rate Limiting

In-memory rate limiting rejects IP addresses exceeding 5 failed login attempts in 60 seconds with HTTP 429.

4. Method-Level RBAC

Enforced twice: at HTTP security filter level and service method level using Spring @PreAuthorize annotations.

5. IDOR Defense

Resource access validates caller ownership on the server; employees cannot inspect other staff members' data or orders.

6. HTTP Security Headers

Strict Content-Security-Policy (CSP), X-Frame-Options: DENY, X-Content-Type-Options: nosniff, and HSTS enabled.

7. PII Scrubbing in ETL

The analytics ETL pipeline strictly scrubs emails, phone numbers, and salaries before loading into the warehouse.

8. Correlation IDs

Production errors mask internal stack traces, returning a unique correlation UUID for server-side troubleshooting.

FR-AUTH
Authentication & User Specifications
  • FR-AUTH-1: A user can log in with valid email/password and receives a cryptographically signed JWT token.

  • FR-AUTH-3: Every API endpoint requires authentication except /api/auth/login and health checks.

  • FR-AUTH-5: Repeated failed login attempts (5 per minute) are rate-limited with HTTP 429.
FR-ORD
Sales Order Processing Specifications
  • FR-ORD-1: Order line item calculations and discounts are strictly validated on the server. Client totals are ignored.
  • FR-ORD-2: Order status must strictly follow the workflow: INQUIRY → QUOTED → CONFIRMED → PAID → DELIVERED.
  • FR-ORD-3: Orders may transition to CANCELLED only before reaching the DELIVERED state.
  • FR-ORD-4: Every status transition must record an audit entry in order_status_history.
  • FR-ORD-5: Order discounts are restricted between 0.00% and 30.00%. Quantities must be greater than or equal to 1.

Technical Architecture Specification

Technical Requirements Document (TRD)

How the system is technically designed: layered patterns, database schemas, REST conventions, JWT security lifecycle, and testing frameworks.

What is a Technical Requirements Document (TRD)?
While the PRD defines the business vision and functional requirements, the TRD establishes HOW the system is engineered. It details the layered architecture, design principles, database normalization, API schemas, security token lifecycle, and testing standards.

Architectural Principles

5 foundational engineering decisions governing the codebase

1. Layered Monolith Core

Strict Separation of Concerns: Controller → Service → Repository. Controllers never contain business logic; services never return raw database entities to controllers.

2. Isolated Storage Schemas

Operational data (public) and warehouse data (dw) reside in separate schemas with dedicated database users adhering to least privilege.

3. Server Decides All

Product prices, discounts, line totals, and user permissions are computed exclusively on the server. Client input totals are ignored.

4. Fail-Fast Validation

DTOs validated immediately using Bean Validation (@Valid). Errors trigger a standardized JSON payload with field errors and correlation UUIDs.

5. Resilient Degradation

If the Python analytics service is unreachable, Spring Boot returns a graceful HTTP 503 while CRUD management continues uninterrupted.

6. Zero PII in Warehouse

The analytics warehouse intentionally holds no staff salaries, customer emails, or telephone numbers, aligning with data privacy best practices.

The 6-Stage ETL Pipeline

How data flows from 3 heterogeneous sources into clean warehouse star schema

1. Extract

Reads transactional data from PostgreSQL (S1), 3-year historical sales CSV (S2), and customer review feedback CSV (S3).

2. Clean

Drops duplicate records, validates date formats, handles nulls (median for numeric, "Unknown" for categorical), and logs rejected rows.

3. Normalize

Standardizes region spellings (North, South, East, West, Central), lowercases text, and cleans review punctuation.

4. Transform

Calculates measures: revenue = qty × price, profit = revenue - cost, and computes Recency-Frequency-Monetary (RFM) metrics.

5. Enrich

Scrubs PII (removes email, phone, salaries), tags source provenance, and runs TextBlob sentiment analysis on reviews.

6. Load

Idempotently upserts dimension records and replaces fact tables inside an atomic PostgreSQL transaction. Logs run stats.

Core Analytical SQL Queries

Real SQL queries executed against the star schema for executive insights

Month-over-Month Revenue Growth with LAG()
WITH monthly AS ( SELECT d.year, d.month, SUM(f.revenue) AS rev FROM dw.fact_sales f JOIN dw.dim_date d USING (date_key) WHERE f.order_status IN ('PAID', 'DELIVERED') GROUP BY d.year, d.month ) SELECT year, month, rev, ROUND(100.0 * (rev - LAG(rev) OVER (ORDER BY year, month)) / NULLIF(LAG(rev) OVER (ORDER BY year, month), 0), 2) AS growth_pct FROM monthly;
Customer RFM Matrix for K-Means Clustering
SELECT c.customer_key, c.name AS customer_name, CURRENT_DATE - MAX(d.full_date) AS recency_days, COUNT(DISTINCT f.order_id) AS frequency, SUM(f.revenue) AS monetary_total FROM dw.fact_sales f JOIN dw.dim_customer c USING (customer_key) JOIN dw.dim_date d USING (date_key) GROUP BY c.customer_key, c.name;

Viva Defense Cheat Sheet

Quick, high-scoring answers to the 5 most common questions asked by academic examiners:

Q1: Why separate PostgreSQL schemas (public vs dw)?

Answer: "Operational OLTP systems require normalized tables to ensure fast ACID transactions without update anomalies. Analytical OLAP systems require denormalized Star Schemas (facts + dimensions) to enable fast multi-table aggregations without slowing down daily CRUD operations."

Q2: How does the Holt-Winters Forecast work?

Answer: "We use statsmodels Exponential Smoothing. It models historical monthly sales trends. We validate model accuracy using MAPE (Mean Absolute Percentage Error) and generate 95% confidence intervals from residual standard deviations."

Q3: Where is the JWT token stored and validated?

Answer: "In an httpOnly cookie to prevent XSS attacks. Every incoming request passes through JwtAuthFilter, which parses the HS256 signature, extracts the user role, and sets the Spring SecurityContext."

Q4: Why use a separate Python service instead of Java?

Answer: "Python provides industry-standard data science libraries (Pandas, scikit-learn, TextBlob). Keeping it as an independent microservice ensures that intense ML computation never blocks Java transactional CRUD threads."

Q5: What prevents employees from seeing other staff salaries?

Answer: "Role-Based Access Control and DTO mapping. In EmployeeService, salary fields are scrubbed from response DTOs unless the caller possesses the ADMIN role."
